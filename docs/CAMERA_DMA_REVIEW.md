# Проверка DMA-буфера OV2640 и исправление VSYNC

## Найденная причина

На подключённом модуле OV2640 штатная настройка DCMI_VSPOLARITY_HIGH
давала таймаут: счётчик DMA оставался 38400. При смене на
**DCMI_VSPOLARITY_LOW** snapshot успешно принял 153600 байт RGB565 320×240;
Python-клиент сохранил настоящее изображение комнаты.
Это результат проверки данного модуля, а не предположение по успешному SCCB.

Исправление находится в `Core/Src/camera_stream.c`, функция `camera_hardware_init()`.
HREF остаётся HSPOLARITY_LOW, приём данных — PCKPOLARITY_RISING.
На время диагностики переключение было выполнено через SWD, затем
исправление перенесено в исходники main.

## Что проверено в буфере и DMA

| Проверка | Результат |
|---|---|
| Адрес буфера в проверенном ELF | 0x24005BA0; при новой сборке адрес может измениться |
| Область памяти | AXI SRAM RAM_D1, не DTCM |
| Размер | 320×240×2 = 153600 байт |
| Выравнивание | 32 байта; конец буфера также кратен 32 |
| Длина HAL_DCMI_Start_DMA | 38400 слов по 4 байта; менее лимита 65535 |
| DMA | DMA2_Stream0, peripheral-to-memory, word/word, MINC, FIFO |
| Источник | DCMI_DR, 0x48020028 |
| Назначение | Фактический адрес frame, без конфликта с lwIP heap в D2 |
| DMAMUX1 Channel8 | CCR=0x4B, запрос DCMI |
| D-cache на проверенной плате | Выключен: SCB_CCR=0x40200, бит DC не установлен |
| Тест реального DMA2_Stream0 | 32 слова скопированы из AXI SRAM в начало frame, все значения совпали, NDTR=0 |

В тесте memory-to-memory процессор был остановлен, проверяемые данные и
регистры сохранены. После теста восстановлены буфер/регистры, CPU продолжил
выполнение. Этот тест проверяет доступ DMA2 к буферу; отдельно путь запроса
DCMI проверен последующим реальным захватом.

DMA1/DMA2 на STM32H755 могут передавать данные DCMI в AXI SRAM D1:
[ST AN5020, раздел 3.2.4.2, рисунок 10](https://www.st.com/resource/en/application_note/an5020-digital-camera-interface-dcmi-on-stm32-mcus-stmicroelectronics.pdf).
Перенос буфера в SRAM D2 для исправления этой неисправности не понадобился.

## Сравнение полярностей

Для диагностики временно использован continuous grab, без выполнения CPU
и без изменения flash; за каждым вариантом наблюдали 1 секунду. Результаты
не равнозначны валидному snapshot, но помогли локализовать неисправность:

| HSPOL / VSPOL | Остаток DMA | Что установлено |
|---|---|---|
| LOW / HIGH (исходный вариант) | 38400 | Ни одного слова |
| LOW / LOW | 0 | Весь объём передан |
| HIGH / HIGH | 13493 | Частичный приём; пригодность изображения не проверялась |
| HIGH / LOW | 10526 | Частичный приём; пригодность изображения не проверялась |

После этого вариант LOW/LOW проверен обычным snapshot через существующий
UDP-протокол и Python-клиент: получен реальный кадр, а не тестовые полосы.

## Хвост потока после полезного изображения

Измерение snapshot в отдельной области SRAM с запасом показало **153632 байта**:
на 32 байта больше payload RGB565. При размере DMA ровно 153600 после
заполнения памяти возникает OVR, хотя изображение уже попало в буфер.
Поэтому только смена полярности не обеспечила устойчивую работу после reboot.

Теперь frame выделен на **153728 байт**: 153600 полезных + 128 байт запаса.
DMA запускается на 38432 слова. FRAME interrupt включается до старта,
захват завершается по аппаратному концу кадра; проверяется, что передано
не менее 38400 слов. Только полезные 153600 байт идут клиенту.
При неполном кадре возвращается ошибка и UART last=short-frame.
Защитный хвост не является частью изображения.

При последней проверке remaining=31: приняты payload и 4 хвостовых байта.
В диагностическом опыте без выполнения CPU приняты 32 хвостовых байта.
Величина хвоста зависит от момента обработки окончания, поэтому фиксированное
число 153632 не используется как обязательная длина каждого кадра.

## Ещё одно исправление при обзоре кода

Локальная реализация HAL_DCMI_IRQHandler после snapshot отключает
LINE/VSYNC/ERR/OVR interrupts. HAL_DCMI_Start_DMA не включает их обратно.
Поэтому перед каждым новым захватом код:

1. Останавливает предыдущий захват.
2. На время перенастройки отключает FRAME interrupt и очищает оставшиеся флаги FRAME/OVR/ERR/VSYNC/LINE.
3. Включает FRAME/LINE/VSYNC/ERR/OVR interrupts.
4. Сбрасывает сохранённый HAL DCMI ErrorCode для новой попытки.
5. Запускает DMA snapshot.

FRAME interrupt больше не зависит от заполнения всего защитного хвоста.
В результате не используется старый FRAME-флаг после таймаута,
а ошибки следующих кадров остаются наблюдаемыми через IRQ и UART.

## Как проверить

После прошивки исправленного main используйте обычный клиент:

```bash
cd ~/projstm/camera_client
.venv/bin/python client.py 192.168.1.123
```

В UART (115200 8N1) введите `camera` или `camera watch on`.
Ожидается рост frames и `last=frame-ok remaining=N`, где 0 <= N <= 32. При активном snapshot
remaining уменьшается, но UART-снимок может не успеть показать промежуточное
значение. Реальный размер кадра не менялся, клиент не требует нового формата.

Правильная VSYNC и успешный DMA не гарантируют качество цветов и отсутствие
помех при длинных проводах; это оценивается по изображению и осциллограммам.

## Проверка исправленного main на плате

После записи flash с verify приняты **пять последовательных настоящих кадров**,
153600 байт каждый. UART: `frames=5 errors=0`, `last=frame-ok remaining=31`,
коды DMA/DCMI равны нулю. Изображения различаются между кадрами.
Сборка ARM GCC и host-тесты CLI/settings прошли.

На части кадров видны цветные полосы и зерно. Причина этих артефактов не
установлена: успешный захват и исправление объёма DMA не доказывают качество
электрических сигналов и настройки DSP. Для дальнейшей проверки нужны
осциллограммы и оценка проводки; клиентский формат RGB565 не менялся.

Примеры и UART-лог сохранены в `~/Рабочий стол/camera-dma-review/`.

Полное описание алгоритма, платы и карты функций: [CAMERA_ARCHITECTURE.md](CAMERA_ARCHITECTURE.md).

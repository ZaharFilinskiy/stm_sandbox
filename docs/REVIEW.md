# Разбор проекта

Проверено исходное состояние на `1f2a7fe` вместе с существовавшими локальными
изменениями `Core/Src/main.c`. Это перспективный аппаратный прототип;
до эксплуатационной прошивки ему прежде всего нужны предсказуемая обработка
ошибок, проверенный загрузчик и испытания на плате.

## Сильные стороны

- Есть соединённые подсистемы: HAL, LAN8742, lwIP, UART line editor,
  FreeRTOS, отдельный загрузчик, заготовки RTC/I2C/дисплея.
- Сетевой интерфейс и PHY вынесены из main; CLI-библиотека умеет редактирование
  строки и историю. Их можно использовать без написания собственного парсера.
- Есть GCC/Make-сборка и явная карта памяти. Vendor-исходники доступны локально,
  что позволяет изучать фактическое поведение HAL и ядра.
- Использован preemptive FreeRTOS, есть `configASSERT` и диагностические API.
  Приоритет USART3=6 совместим с `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5`.

## Найденные ошибки и изменения

| Исходная проблема | Последствие | Выполненное изменение |
|---|---|---|
| `SysTick_Handler` вызывает только `HAL_IncTick` | Нет RTOS tick: нарушены задержки и time slicing | Вызов `xPortSysTickHandler` после запуска scheduler |
| `uartProc` вызывает `HAL_UART_Receive_IT`, затем сразу читает `ch` | Запуск операции ошибочно считается завершением приёма | Копирование из ISR в очередь; CLI ожидает очередь |
| Callback передаёт `&huart`, где параметр уже указатель | Неверный тип/адрес HAL handle | Callback использует непосредственно `uart` |
| ISR уведомляет `uartSend`; байт не передаётся | Клавиша запускает Ethernet/служебный вывод вместо CLI | Убрана экспериментальная третья задача |
| lwIP и UART крутятся без блокировки | Постоянная загрузка CPU, Idle не получает времени | Ожидание очереди; задержка сети в 1 тик |
| `sys_check_timeouts` вызывается дважды | Избыточная обработка таймеров | Оставлен вызов внутри `MX_LWIP_Process` |
| CLI, `uartSend` и ETH init используют UART TX | Конфликты HAL_BUSY и смешанный вывод | UART TX принадлежит CLI, конечный timeout |
| Не проверено создание третьей задачи и возврат scheduler | Необработанная нехватка памяти | Проверки очереди/задач, hooks malloc failure/stack overflow |
| RX size 1524 против 1536; RX descriptors используют TX count | Несогласованный контракт HAL | Параметры согласованы |
| UART теряет часть команды при ошибке | Возможно исполнение усечённой команды | Счётчики, восстановление RX, отбрасывание строки |
| `VTOR` зависит только от загрузчика | Отладчик может запустить приложение с чужими векторами | main устанавливает свою таблицу |
| IP захардкожен | Нет конфигурации устройства | Настройки, boot snapshot, CLI и Flash |
| TFTP writer без границ и синхронизации | Порча других областей/конфликт HAL | Mutex, предел неактивного слота 384 KiB, целые flashwords |

Задача не вызывается как функция из прерывания: ISR делает её готовой,
передавая байт очереди. Это схема из документации
[FreeRTOS: interrupt management](https://github.com/FreeRTOS/FreeRTOS-Kernel-Book/blob/main/ch07.md).
Размещение настроек рассчитано на 2 MiB Flash STM32H755xI; параметры сверены
с локальным CMSIS/HAL и [datasheet ST](https://www.st.com/resource/en/datasheet/stm32h755ii.pdf).

## Архитектура после изменений

`main.c` отвечает за периферию, запуск двух задач и UART transport. `app_cli.c`
владеет редактором строки и командами. `settings.c` не зависит от HAL/RTOS и
тестируется на ПК. `settings_flash.c` реализует backend; `flash_access.c`
координирует писателей одного ядра. `lwi.c` получает неизменяемую конфигурацию
загрузки. Из CLI не вызывается raw lwIP API.

`NO_SYS=1` допустим при единственном владельце стека. Для сетевых операций
из других задач потребуется очередь запросов этому владельцу либо
полноценная интеграция `tcpip_thread` и `NO_SYS=0`. Подключение FreeRTOS
само по себе не делает raw API lwIP потокобезопасным.

## Что ещё нужно улучшить

1. **Загрузчик/TFTP — главный оставшийся риск.** `Core/startrc/main.c` ищет
   первое не-`0xFFFFFFFF` слово без границы и проверки MSP/Reset_Handler.
   Нет проверки целостности образа, подтверждения загрузки, rollback.
   В TFTP выбор слота по `BOOT7_CUR` не согласован с linker layout, чтение —
   заглушка, нет подготовки/стирания полноценного образа и обработки произвольного
   последнего блока. Добавленные ограничения предотвращают выход за слот,
   но не превращают этот код в готовый updater. Пакеты, чья длина не кратна
   32, теперь отклоняются вместо чтения за концом буфера. Неиспользуемая
   `resetaftcloe` получает mutex и отказывается стирать область с текущей
   таблицей векторов; её дизайн всё равно требует замены.
2. **Кеш и DMA.** Дескрипторы выровнены на 32, но секции не размещены явно
   в linker script: текущая сборка кладёт их в AXI SRAM. Нет полного контракта
   MPU/cache maintenance. До включения D-cache необходимо проверить descriptors,
   RX pool и TX pbuf; одного alignment недостаточно. Адрес lwIP heap
   `0x30044000` задан вручную и не зарезервирован секцией линкера.
3. **Восстановление.** Fault handlers и `Error_Handler` висят бесконечно;
   watchdog выключен. Нужны сохранение причины reset/fault и обработка ошибок
   подсистем без остановки всей прошивки. RTC каждый старт задаёт дату/время
   заново, уничтожая смысл сохранённого времени.
4. **Разделение кода.** main всё ещё содержит большой блок периферии и
   закомментированный код. Следующий шаг — `board_init`, `uart_transport`,
   `network_service`. `main.h` включает дисплей и lwIP для всех потребителей;
   зависимости широкие.
5. **Flash и питание.** Новый контракт Bank 2 нужно согласовать с CM4.
   A/B+CRC защищает на уровне формата; аппаратные ECC, brownout и NMI
   при обрыве программирования пока не покрыты испытаниями. Для частых записей
   нужен журнал/wear leveling вместо стирания сектора на каждое изменение.
6. **Сборка.** Исправлена зависимость от POSIX `find`, конфликтовавшего с
   Windows `find.exe`; добавлены зависимости от заголовков/linker script,
   устранена гонка `size` с линковкой при `make -j`. Список HAL-модулей теперь
   явный. Остаются предупреждения в старых embedded_cli, ether, TFTP и PHY,
   нет политики warnings/CI и зафиксированной версии toolchain. Комментарий
   FreeRTOSConfig говорит V10.2.1, фактическое ядро — V11.3.1.

## Git

История компактная: 15 коммитов, этапы PHY → CLI → FreeRTOS видны. Плюс —
отдельные коммиты добавления подсистем и игнорирование `build/`. Минус —
несколько последовательных коммитов `.gitignore` и названия вроде
`fix: main module`: по ним нельзя понять причину и эффект изменения.
Тестов приложения и CI в исходном состоянии не было; README состоял из строки.
Большая часть 1786 отслеживаемых файлов — vendor-код, поэтому размер репозитория
плохо отражает размер собственного приложения.

Практические улучшения: один коммит на связное изменение с описанием причины,
отдельные обновления vendor-кода, версии зависимостей/toolchain,
автоматическая сборка и host-тесты на PR, теги проверенных прошивок.
Добавленные host-тесты — первая основа, не замена испытаниям на MCU.
Исходная незакоммиченная работа main учитывалась; коммиты, reset и изменения
истории Git в рамках этой задачи не выполнялись.

# Как STM32 управляет OV2640 и как посмотреть диагностику через UART

Документ для ветки **main**, платы **NUCLEO-H755ZI-Q / MB1363**, CM7.
Пошаговая проводка с номерами разъёмов находится в [CAMERA_OV2640.md](CAMERA_OV2640.md).
Здесь описаны настройки прошивки и смысл диагностических сообщений.
Ветка main захватывает настоящую камеру. Тестовое изображение относится
к отдельной ветке testpattern; её режим не добавлен в main.

## 1. Какие сигналы STM32 выдаёт, а какие принимает

Не все контакты камеры являются выходами STM32. Он выдаёт тактирование,
сброс и управление сном, а данные и синхронизацию получает от камеры.

| GPIO STM32 | Контакт камеры | Режим STM32 | Кто формирует сигнал |
|---|---|---|---|
| PA8 | XCLK | AF0, MCO1, push-pull | STM32, постоянное тактирование 16 МГц |
| PD4 | RET / RESETB | GPIO output push-pull | STM32, сброс камеры низким уровнем |
| PD5 | PWDN | GPIO output push-pull | STM32, высокий уровень переводит камеру в сон |
| PB10 | SIOC | AF4, I2C2_SCL, open-drain | STM32 задаёт такты управления SCCB |
| PB11 | SIOD | AF4, I2C2_SDA, open-drain | Двунаправленная линия управления |
| PA6 | PCLK | AF13, DCMI_PIXCLK | Камера выдаёт тактирование данных |
| PA4 | HREF | AF13, DCMI_HSYNC | Камера обозначает полезные данные строки |
| PB7 | VSYNC | AF13, DCMI_VSYNC | Камера обозначает синхронизацию кадров |
| PC6, PC7, PC8, PC9 | D2, D3, D4, D5 | AF13, DCMI_D0…D3 | Камера выдаёт четыре младших бита принятого байта |
| PE4, PD3, PE5, PE6 | D6, D7, D8, D9 | AF13, DCMI_D4…D7 | Камера выдаёт четыре старших бита принятого байта |

`GPIO_MODE_AF_PP` для контактов DCMI подключает альтернативную функцию:
DCMI использует их как входы. Запись AF_PP не означает, что STM32 должен
выдавать данные на эти контакты. Направление определяется периферией.

Сигналы D2–D9 на вашем модуле — Y2–Y9 сенсора. Для 8-битного интерфейса
D2 камеры становится DCMI_D0 STM32, D9 камеры — DCMI_D7.

## 2. Где искать код и в каком порядке он выполняется

- `Core/Src/main.c`: HAL, системные часы, UART3, I2C1, запуск FreeRTOS.
- `Core/Src/stm32h7xx_hal_msp.c`: назначение USART3 PD8/PD9, I2C1 PB6/PB9,
  Ethernet RMII.
- `Core/Src/camera_stream.c`: GPIO камеры, MCO1, I2C2, DCMI/DMA, SCCB,
  захват, UDP, сбор диагностических данных.
- `Core/Inc/ov2640_settings.h`: последовательности настройки DSP сенсора.
- `Core/Inc/ov2640_regs.h`: имена регистров OV2640.
- `Core/Src/app_cli.c`: команды и печать в UART.
- `Core/Inc/camera_stream.h`: структура CameraDiagnostics для обмена между задачами.

В `SystemClock_Config()` выбран HSI без PLL: SYSCLK/HCLK/APB равны 64 МГц.
Задача `lwipProc` запускает Ethernet/lwIP, затем `camera_stream_init()`.
Она же вызывает `camera_stream_poll()` и единолично обслуживает raw API lwIP,
поскольку `NO_SYS=1`. Задача `uartProc` принимает команды и печатает отчёты.

## 3. Включение тактирования портов и выбор альтернативной функции

В `camera_hardware_init()` включаются GPIOA…GPIOE, I2C2, DCMI и DMA2 через
`__HAL_RCC_*_CLK_ENABLE()`. Без тактирования периферии настройки не заработают.

Помощник `configure_gpio_pins(port, mask, af, mode)` заполняет `GPIO_InitTypeDef`:
`Pin`, `Mode`, `Pull=GPIO_NOPULL`, `Speed=GPIO_SPEED_FREQ_VERY_HIGH`, `Alternate`.
Затем `HAL_GPIO_Init()` задаёт режим и мультиплексор выводов.

Номер AF выбирается по таблице альтернативных функций STM32H755.
AF0 на PA8 подключает MCO; AF4 на PB10/PB11 подключает I2C2;
AF13 на выбранных входах подключает DCMI. Нельзя произвольно переставить
сигнал на любой свободный GPIO: сначала нужно проверить его поддержку в таблице AF.

`GPIO_SPEED_FREQ_VERY_HIGH` задаёт характеристики драйвера GPIO, а не
частоту сигнала. Частоту XCLK задаёт источник и делитель MCO1.

## 4. Как получен XCLK на PA8

```c
pins(GPIOA, GPIO_PIN_8, GPIO_AF0_MCO, GPIO_MODE_AF_PP);
HAL_RCC_MCOConfig(RCC_MCO1, RCC_MCO1SOURCE_HSI, RCC_MCODIV_4);
```

MCO1 выводит внутренний HSI наружу: 64 МГц / 4 = **16 МГц**.
Период около **62.5 нс**. Сигнал генерируется аппаратно и не зависит от
планировщика FreeRTOS. HAL_GPIO_WritePin для его переключения не нужен.
Камера получает XCLK и на его основе формирует собственный PCLK.

При измерении используйте короткую землю и согласованный коэффициент щупа.
Если сигнал нормальный на PA8, но искажён на модуле, проверяйте проводку.
UART выводит ожидаемую настройку XCLK; он не измеряет реальную частоту.

## 5. RESETB и PWDN

PD4/PD5 настроены как обычные выходы push-pull. Последовательность:

1. PD4=0: камера удерживается в сбросе.
2. PD5=0: аппаратный сон выключен.
3. Ожидание 5 мс.
4. PD4=1: сброс отпущен.
5. Ожидание 10 мс перед SCCB.

Позднее выполняется программный сброс записью COM7_SRST и ожидание 10 мс.
RET модуля не соединяется с NRST Nucleo: сброс камеры управляется отдельно.

## 6. Настройка камеры через SCCB на I2C2

PB10/PB11 настроены open-drain без внутренних подтяжек. Нужны внешние
подтяжки SIOC/SIOD к 3.3 В, обычно около 4.7 кОм, если их нет на модуле.
Open-drain позволяет участникам шины тянуть линию вниз; высокий уровень
обеспечивает резистор. Push-pull для этих линий не используется.

I2C2 работает с 7-битными адресами. Сенсор имеет адрес **0x30**;
STM32 HAL принимает адрес со сдвигом на один бит, то есть **0x60**.
`Timing=0x70421F2F` рассчитан в проекте на kernel clock 64 МГц и около 100 кГц.
При изменении системных часов это значение необходимо пересчитать.

`camera_write_register()` отправляет адрес регистра и его значение. `camera_read_register()` сначала передаёт
номер регистра, завершает операцию STOP, затем читает байт отдельно.
Банк выбирается записью регистра 0xFF: 1 — sensor, 0 — DSP.
Из sensor-регистров 0x0A и 0x0B читается PID: ожидается **0x2642**.

После проверки PID записываются базовые таблицы, окно SVGA, масштабирование
320×240 и режим RGB565. Автоматические функции экспозиции/усиления/DSP
задаются таблицами. Прошивка не меняет формат камеры во время каждого кадра.

## 7. DCMI и DMA

DCMI принимает аппаратные HREF/VSYNC/PCLK и восемь бит данных:

- аппаратная синхронизация, приём по нарастающему PCLK;
- VSPOLARITY_LOW (подтверждено захватом с вашего модуля), HSPOLARITY_LOW для активного HREF;
- 8-битная шина, RGB565, JPEG выключен;
- приём всех байтов/строк, snapshot — один кадр на запрос.

DMA2_Stream0 получает запрос DMA_REQUEST_DCMI. Направление — периферия
в память. Адрес DCMI_DR не увеличивается, адрес памяти увеличивается.
Выравнивание периферии и памяти — word, FIFO включён, режим normal.
DCMI собирает байты интерфейса в 32-битные слова для DMA.

Полезное изображение содержит 320×240×2 = **153600 байт**, то есть **38400 слов**.
Буфер DMA имеет запас 128 байт: **153728 байт / 38432 слова**.
Буфер в AXI SRAM 0x24000000, выравнивание 32 байта. При включённом D-cache
перед DMA выполняется clean/invalidate, после завершения invalidate.

`__HAL_LINKDMA()` связывает HAL handles DCMI и DMA. IRQ DMA2_Stream0 и DCMI
имеют приоритет 6 и передаются HAL обработчикам. Callback FRAME выставляет
флаг готовности, callback ошибки — флаг отказа; в IRQ UART не используется.
`camera_stream_poll()` завершает обработку в контексте задачи.

FRAME interrupt включается перед snapshot. По концу кадра проверяется,
что DMA передало не менее 38400 слов полезного изображения. Запас позволяет
принять хвостовые байты до события FRAME без переполнения. Если payload
неполный, отчёт показывает short-frame. По истечении 3 с захват
останавливается и фиксируется таймаут.

## 8. Как открыть UART-консоль

Параметры: **115200 бод, 8 бит, без чётности, 1 стоп-бит (8N1)**,
без аппаратного flow control. Используется USART3:

| Сигнал | GPIO | Внешний USB-UART адаптер |
|---|---|---|
| TX STM32 | PD8 | Соединить с RX адаптера |
| RX STM32 | PD9 | Соединить с TX адаптера |
| Земля | GND | Соединить с GND адаптера |

Используйте UART с логическими уровнями 3.3 В, не интерфейс RS-232.
На штатной Nucleo USART3 подключён к ST-LINK Virtual COM Port согласно
UM2408 раздел 7.9. Если перемычки платы изменены, проверьте разводку VCP.
В Linux устройство обычно `/dev/ttyACM0`, но фактический номер может отличаться.
Подключите USB к ST-LINK и откройте порт в вашем терминале.

## 9. Команды диагностики

```text
camera
camera watch on
camera watch off
```

`camera` печатает один подробный отчёт. `camera watch on` включает отчёты
примерно раз в секунду; `off` выключает. После завершения инициализации
один отчёт появляется автоматически, если консоль свободна.
Если вводится команда, периодическая печать откладывается до завершения
ввода, чтобы не мешать строке. Если терминал открыт после старта платы,
введите `camera`: стартовое сообщение не повторяется само.

Пример **пояснения формата**, не гарантия текущего состояния платы:

```text
CAM state=ready init=0 PID=0x2642 XCLK=HSI/4 (expected 16000000 Hz)
CAM SCCB status=0 error=0x00000000 failed-bank=0x00 reg=0x00
CAM frames=0 errors=1 capturing=0 valid=0 id=0x12345678 age=0 ms
CAM UDP requests=12 replies=12 send-errors=0
CAM live: DMA remaining=38432 words (payload=38400, capacity=38432) err=0x00000000 DCMI err=0x00000000
CAM DCMI CR=... SR=... RIS=...
CAM last=timeout remaining=38432 DMA-err=0x00000000 DCMI-err=0x00000000
CAM pre-stop CR=... SR=... RIS=...
CAM GPIO sample: HREF(PA4)=1 VSYNC(PB7)=0 PCLK(PA6)=1 RESET(PD4)=1 PWDN(PD5)=0
```

| Поле | Как читать |
|---|---|
| state / init | initializing до завершения; 0 ready, 1 HAL-init-error, 2 SCCB-or-PID-error, 3 register-write-error |
| PID | Прочитанный ID, ожидается 0x2642; частичный/нулевой ID возможен при отказе чтения |
| SCCB status | Последний отказ HAL: 0 нет зафиксированного отказа, 1 ERROR, 2 BUSY, 3 TIMEOUT |
| error | Текущий код I2C HAL; описание битов в stm32h7xx_hal_i2c.h |
| failed-bank / reg | Банк и регистр последнего отказа SCCB; нули сами по себе не являются ошибкой |
| frames / errors | Успешные кадры / ошибки захвата |
| capturing / valid | Идёт захват / буфер содержит завершённый кадр |
| id / age | ID текущего UDP-кадра и время активного захвата; age=0 после остановки |
| requests / replies / send-errors | Принятые корректные запросы CAM1, успешные передачи в lwIP, ошибки отправки/выделения pbuf; replies не означает подтверждение доставки ПК |
| DMA remaining | Остаток слов в буфере DMA: 38432 означает ни одного; при frame-ok остаток 0…32 допустим, это незаполненный запас |
| last | Последний результат: none, start-error, DCMI-error, timeout, frame-ok, short-frame |
| pre-stop | CR/SR/RIS и ошибки, сохранённые до HAL_DCMI_Stop |
| GPIO sample | Одиночные уровни входов и выходов; это не измерение частоты и не доказательство наличия импульсов |

CR/SR/RIS выводятся в hex для сопоставления с reference manual STM32H755.
Ошибки HAL DMA расшифровываются по stm32h7xx_hal_dma.h, DCMI — по
stm32h7xx_hal_dcmi.h. Ненулевой RIS после таймаута помогает отличить
появление событий синхронизации от полного отсутствия активности.

## 10. Как получить полезный лог неисправности

1. В UART введите `camera`, затем `camera watch on`.
2. Запустите обычный Python-клиент без `--test-pattern`.
3. Дождитесь ошибки или появления изображения.
4. Введите `camera watch off`, затем `camera` и сохраните полный отчёт.

Если PID верный и init=0, управление SCCB сработало. Если после запроса
last=timeout, remaining=38432, DMA не получило данных: проверяйте PCLK,
HREF, VSYNC и их полярности. При частично уменьшившемся remaining приём
начался, но объём не достигнут: проверяйте размеры, синхронизацию, сигнал
и коды ошибок. remaining больше 32 при событии FRAME означает недостаточный объём данных
и приводит к short-frame. Нулевой remaining вместе с OVR может означать,
что фактический поток превысил даже размер с запасом.

Для диагностики используются копии состояния: только lwipProc читает HAL
handles и публикует snapshot раз в 25 мс и при завершении захвата.
Короткая critical section защищает копирование между задачами; печать
выполняется после выхода из неё. UART не блокирует UDP внутри сетевого
callback и не вызывается из IRQ. Вывод по watch добавляет нагрузку задаче
CLI, поэтому для длительной обычной работы отключайте его.

## 11. Сборка и проверка

```bash
cd ~/projstm/stm_sandbox
git branch --show-current  # должно быть main
make -j4
python3 tests/run_host_tests.py
```

Готовый ELF: build/stm32h755_cm7.elf. Host-тесты проверяют команды camera,
watch on/off, отсутствие периодической печати во время ввода и старые
команды CLI. Успешная сборка не заменяет проверку сигналов на плате.

Проверка DMA и исправление полярности VSYNC описаны в
[CAMERA_DMA_REVIEW.md](CAMERA_DMA_REVIEW.md). На плате получен реальный кадр OV2640.

Полное описание алгоритма, платы и карты функций: [CAMERA_ARCHITECTURE.md](CAMERA_ARCHITECTURE.md).
